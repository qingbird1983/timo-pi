# P-016 错误隔离会改变派发返回值

## 现象

把 `dispatch_all` 从「单个扩展派发失败即 `return Err`」改为「记诊断后 `continue`」后，两个既有预算测试立刻变红：`handler_exceeding_budget_reports_e301` 与 `context_is_reusable_after_budget_interrupt` 原本断言 `dispatch(...).unwrap_err()`，实际拿到 `Ok(Null)`。另一条新写的负对照（工具调用不传取消标志、仍按预算收敛）则直接挂死。

## 根因

1. **语义面比描述更大**：设计 §8 说的是「单 handler 失败继续下一个」，实现粒度是「单扩展」；改动同时改变了**整次派发的返回值**——全部 handler 失败时不再冒泡，而是返回 `Null`（诊断里有 E301/E302）。既有测试把「唯一 handler 失败」等同于「整次派发失败」。
2. **预算不是全链路事实**：hook 派发有 30s 预算（`invoke(..., Some(budget), ...)`），扩展**工具调用**传的是 `budget=None`。工具本身没有预算兜底，取消是唯一收敛手段；负对照的前提不成立。

## 修复

- 两个预算测试改为断言：派发返回 `Null` + `diagnostics_for` 含 E301；第二次派发仍成功。
- 取消测试拆到 `crates/timo-ext/tests/cancel.rs`，删除「无取消仍按预算收敛」的负对照；保留「预置取消标志 → 立即返回 E301」。
- 取消标志在宿主层统一映射为 E301（JS 中断可能表现成 E302，不能直接断言原始码）。

## 预防

1. **改错误处理语义前，先列出所有消费端断言**：不只问「后续还执行吗」，还要问「失败时整体返回什么」。
2. **预算/超时按路径核对**：hook 有预算、工具调用无预算；不要把一条路径的默认值套到另一条。
3. 新增负对照先验证前提为真；前提本身不成立时，删掉对照并在注释/踩坑里写清原因，不要为了凑红而保留。
4. 中断类错误对外统一收口（E301），不要依赖底层解释器抛出的具体码。

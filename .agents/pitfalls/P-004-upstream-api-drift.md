# P-004：把上游 API 的二手摘要当成兼容合同

## 现象

架构 04 §1 的事件清单写着支持 `compact`、`error`；按 pi 1.4.0 源码逐项核对时发现：pi **没有** `error` 事件，压缩事件实际是 `session_before_compact`/`session_compact`/`session_compact_failed`。若直接照着早期摘要写 shim，会出现"承诺了不存在的成员、漏掉真实事件名"。

## 根因

- 架构文档是早期调研的**摘要**，不是上游 API 的镜像；摘要会合并/省略/改写成"意思对、名字不对"的条目。
- 兼容矩阵被当成"合同"使用，但没有绑定上游版本，也没有逐项发射点。

## 修复

- Phase 2 设计 05 以 pi 1.4.0 `types.ts` 的 `ExtensionEvent` 联合为唯一清单，逐项标注：状态、发射点、返回值语义。
- 架构 04 加 2026-10-26 修订注记，指向设计 05；不改三分类策略。
- 判定口径写死：**有真实内核发射点才标"支持"**；"成员存在但永不触发"一律标缓做/不支持并诊断。

## 预防

- 任何"兼容上游"的文档必须写明**上游版本**与**对照文件路径**；升级版本即触发逐项复核。
- 摘要只能用于调研，不得直接作为实现契约；写码前回到上游 `types.ts` + 派发实现读一遍。
- 设计文档保留一张"与旧文档校准"表，避免下一位会话再踩同一个名字。

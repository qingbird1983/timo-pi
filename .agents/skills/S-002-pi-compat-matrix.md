# S-002：写"上游兼容矩阵"的方法

## 适用场景

需要把上游框架（pi）的 API 面在自有运行时（Rust + QuickJS）里做兼容，且必须对用户承诺"哪些能用、哪些降级"。

## 前置条件

- 能读到上游**实际源码**（不是博客/摘要），并确认版本号。
- 自有侧已有统一注册表/事件总线/工具元模型（本项目接缝 #2/#4）。

## 步骤

1. **抄清单，不抄结论**：从上游 `types.ts` 的联合类型/接口逐项列出成员（本项目为 41 个事件 + 注册/动作/ctx 面）。
2. **找发射点**：在上游派发实现里逐个确认"何时发、载荷什么、返回值如何合并"（顺序、短路、覆盖、原地改）。
3. **对自有内核找落点**：每个成员标"真实发射点（文件/函数）"或"无落点"。无落点的不许标支持。
4. **四档分类**：支持 / 支持受限 / 缓做（成员存在、返回未实现诊断）/ 不支持（no-op + 诊断）。受限项必须写清差异。
5. **写判定口径**：把"什么算支持"写成一句话，供后续复核；例如"有真实发射点且语义可完整表达"。
6. **留校准表**：旧文档与本表不一致的条目逐条列出，并在旧文档加修订注记（不改历史决策）。
7. **验收锚点**：每个支持项至少对应一个夹具或验收场景；降级项对应诊断断言。

## 验证方法

- 随机抽 5 个"支持"项，能在代码里指出发射点；抽 5 个"不支持"项，订阅后确实只出诊断、不影响会话。
- 用上游真实样本（不入库）跑一遍，观察是否有未列成员触发。

## 失效条件

- 上游改为 semver 承诺并有稳定 SDK；届时可直接依赖 SDK，不需要手写矩阵。
